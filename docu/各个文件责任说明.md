# LinkForge 当前各文件职责说明

本文档用于说明 LinkForge 当前工程中各目录和主要文件的职责，便于后续继续扩展功能时保持清晰的模块边界。

---

# 一、项目根目录

## `.gitignore`

Git 忽略规则文件。

负责声明哪些本地文件不应该提交到 Git 仓库，例如：

* Python 缓存；
* pytest 缓存；
* 虚拟环境；
* IDE 本地配置；
* 日志；
* 数据库；
* API Key；
* Cookie；
* 浏览器登录状态。

它只决定 Git 是否跟踪文件，不会删除本地文件。

---

## `CONTRIBUTING.md`

LinkForge 的开发和协作规范。

主要规定：

* Issue 如何创建；
* 分支如何命名；
* Commit 如何编写；
* Pull Request 如何提交；
* 合并前需要执行哪些测试；
* 哪些敏感信息禁止提交；
* 多人开发时需要遵守什么规则。

它是面向开发者的项目规范，不参与程序运行。

---

## `pyproject.toml`

LinkForge 的 Python 工程核心配置文件。

当前主要负责：

* 项目名称；
* 项目版本；
* Python 版本要求；
* 项目描述；
* Python 包构建方式；
* 运行依赖；
* 开发依赖；
* setuptools 的 `src` 包查找规则；
* pytest 配置；
* Ruff 配置；
* mypy 配置。

后续 Python 工程相关配置应尽量集中在这里维护。

---

## `README.md`

LinkForge 的项目入口文档。

主要负责：

* 说明项目是什么；
* 介绍项目目标；
* 说明当前开发阶段；
* 给出基本安装方法；
* 给出基本使用方法；
* 引导开发者查看其他文档。

README 面向第一次进入仓库的人，不应该塞入过多底层实现细节。

---

## `test_import.py`

迁移阶段用于快速验证 LinkForge 包是否能够正常导入的临时测试脚本。

主要用于验证：

```python
import linkforge
```

以及相关模块导入是否正常。

它不是正式项目结构的一部分。

当对应验证已经由 `pytest` 测试覆盖后，应删除，或者将有价值的测试迁移到 `tests/`。

---

## `verify_syntax.py`

迁移阶段用于快速检查 Python 代码语法的辅助脚本。

正式工程中，语法和代码质量检查应该逐步交给：

* Ruff；
* mypy；
* pytest；
* GitHub Actions CI。

因此该文件属于迁移辅助文件，不应该长期保留在项目根目录。

---

# 九、`src/linkforge/agent/`

Browser Agent 决策和环境交互 Runtime。

---

## `browser.py`

定义 `BrowserAgent` 决策接口：

```text
Observation
    ↓
BrowserDecision
```

它不观察或执行 Browser，也不拥有环境循环。

---

## `loop.py`

定义 `BrowserAgentLoop`，负责：

```text
observe
    ↓
decide
    ↓
execute
    ↓
下一轮 observe
```

它拥有 Browser 环境交互的 `max_steps` 和正常完成语义。

---

## `models.py`

定义：

* `FinishDecision`；
* `BrowserDecision`；
* Browser Agent 与 Loop 之间的结构化决策边界。

---

## `exceptions.py`

定义 Agent Loop 的异常边界，包括：

* `AgentLoopError`；
* `MaxStepsExceededError`。

---

# 十、`src/linkforge/config/`

项目配置模块。

---

## `settings.py`

负责定义和管理 LinkForge 运行配置。

当前主要包括：

* 模型 Provider；
* 模型名称；
* API Base URL；
* 协议类型；
* 默认模型；
* Provider 注册；
* ModelConfig 创建。

该模块只负责“描述配置”。

不应该：

* 调用模型；
* 创建 Agent；
* 执行网络请求；
* 控制浏览器。

真实 API Key 也不应该硬编码在这里。

---

# 十一、`src/linkforge/llm/`

大语言模型适配模块。

目标是：

> 让上层 Agent 不需要关心底层模型到底是 OpenAI、Anthropic 还是其他厂商。

---

## `base.py`

定义 LinkForge 内部统一的 LLM 抽象。

主要包括：

* LLM 抽象接口；
* LLMResponse；
* ToolCall；
* 统一消息相关数据结构。

上层 Agent 应依赖这里的抽象，而不是直接依赖具体 SDK。

---

## `openai.py`

OpenAI 协议适配器。

负责：

* 将 LinkForge 内部消息转换为 OpenAI 消息格式；
* 将 ToolCall 转换为 OpenAI 工具调用格式；
* 调用 OpenAI 或 OpenAI-Compatible 接口；
* 将返回值转换为统一 `LLMResponse`。

它只处理 OpenAI 协议相关逻辑。

---

## `anthropic.py`

Anthropic 协议适配器。

负责：

* 转换 Anthropic 消息格式；
* 处理 System Prompt；
* 转换 Tool Use；
* 转换 Tool Result；
* 调用 Anthropic API；
* 将响应转换成统一 `LLMResponse`。

它只负责 Anthropic 协议差异。

---

## `factory.py`

LLM 工厂模块。

负责根据配置创建不同的 LLM 实现。

例如：

```text
protocol = openai
    ↓
创建 OpenAIInterface
```

或者：

```text
protocol = anthropic
    ↓
创建 AnthropicInterface
```

上层代码只需要请求：

```text
创建一个 LLM
```

而不需要自己判断具体应该实例化哪个类。

这有利于以后增加：

* Qwen；
* DeepSeek；
* Gemini；
* 其他 OpenAI-Compatible Provider。

---

# 十二、Browser 环境边界

Browser Agent 主链路由三个独立 package 组成：

* `src/linkforge/browser/`：定义 Browser 接口和 Playwright 实现；
* `src/linkforge/observation/`：将 Browser 状态捕获为不可变 `Observation`；
* `src/linkforge/action/`：定义结构化 `Action` 并通过 `BrowserActionExecutor` 执行。

这些模块由 `BrowserAgentLoop` 协调，但不依赖具体 LLM Provider。

# 十八、当前 LinkForge 核心调用关系

当前 Browser Agent Runtime 的主要调用关系是：

```text
Browser
    ↓
BrowserObserver
    ↓
Observation
    ↓
BrowserAgent.decide()
    ↓
BrowserDecision
    ↓
BrowserAgentLoop
    ↓
BrowserActionExecutor
    ↓
Browser
    └──────────────→ 下一轮 Observation
```

LLM Infrastructure 是独立的 Provider 边界：

```text
LLMMessage
    ↓
LLM.call_model()
    ↓
OpenAIInterface / AnthropicInterface
    ↓
LLMResponse / ToolCall
```

# 二十一、当前工程中最重要的三个位置

后续开发过程中可以始终记住：

```text
src/linkforge/
```

是：

> 正式代码。

```text
tests/
```

是：

> 对正式代码行为的验证。

```text
pyproject.toml
```

是：

> Python 项目的统一工程配置。

而：

```text
.github/
```

负责：

> GitHub 上的协作和自动检查。

整个 LinkForge 后续功能扩展，都应围绕这几个明确边界继续发展。
