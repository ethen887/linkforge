# Git 与协作流程

## 开始工作

- 先检查当前分支和工作区差异，保留用户已有修改，不覆盖、回退或清理无关内容。
- 每项开发工作对应一个明确的 Issue，并明确目标和验收标准。
- 从最新 `main` 创建功能分支，禁止直接在 `main` 上开发。
- 分支使用 `feature/`、`bug/`、`refactor/` 等常规用途前缀，禁止使用 `codex/` 前缀。
- 提交信息的描述使用中文，保留 Conventional Commit 的类型与可选作用域。
- 继续已有任务时，先确认当前功能分支是否属于该任务；适用时沿用，不重复创建分支或重置已有改动。
- 一个分支原则上只处理一个 Issue，一个 PR 只解决一个明确问题。
- 不混入无关重构或大范围格式化。

## 提交与 Pull Request

- 使用简洁的 Conventional Commit 风格，例如 `feat(browser): ...`、`fix: ...`、
  `refactor: ...`、`chore: ...`；每个提交保持范围集中。
- 使用仓库的 [PR 模板](../.github/pull_request_template.md)，填写关联 Issue（`Closes #123`）、
  修改目的、主要修改、重要设计选择以及实际执行的验证命令。
- UI 或 CLI 的可见变化适合用截图或终端输出说明时，提供经过脱敏的证据。
- 开 PR 前执行 [testing.md](testing.md) 中的完整质量检查；合并前检查代码差异、CI 和评审结果。
- 贡献者流程参见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

## 维护这些规则

- `AGENTS.md` 只维护项目介绍与路由表，具体规则放在仓库根目录的 `ai/`。
- 增加规则文档时，在路由表中写明读取时机；移动文件时同步更新相关链接。
- 每条规则在最相关的文档中维护，其他文档通过链接引用，避免重复维护。
